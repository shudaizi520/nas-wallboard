# NAS Wallboard 收尾修复设计

状态：待用户审阅；此文档不代表代码已经修复或正式版已经更新。

## 目标与边界

用户希望把已经部署的 NAS Wallboard 收尾：日常使用和新用户自行配置都可靠，不丢设置、不把异常数据当成正常值、不因修复增加 NAS 查询负担。

本次以 v1.0.5 为基线，处理上一轮审查列出的缺陷。修复涉及设置接口、采集缓存、备份校验和桌面初始化，按下列独立工作包编写实施计划；每包可以独立测试和审查，最后统一验收发布。

全局约束：

- 保留现有排版、行顺序规则及用户配置；不增加常驻服务。
- 不提高现有采集频率；缓存复用只能减少重复请求，不能用旧数据伪造新的成功时间。
- 天气刷新周期保持：当前天气 10 分钟、分钟降雨 10 分钟、官方预警 5 分钟、日预报 1 小时。
- 不修改 Home Assistant、Plex、旁路由或 NAS 的其他服务；发布时只更新 Wallboard。
- 不返回、记录或提交密码、令牌、Cookie、密钥；已保存的秘密只在服务端使用。
- 保留备份加密、恢复白名单、体积限制、重新认证、事务日志和回滚机制。
- 兼容已有配置；接口增加字段时保留原字段语义，拒绝陈旧写入时给出可恢复的明确提示。
- Windows 实机表现与可在 Ubuntu 运行的核心逻辑测试分开报告，不把后者当成前者。

## 处理方式

采用逐项修复、回归测试和一次正式发布。直接重构整个采集或设置系统会增加迁移风险；只修最显眼的界面问题则不能解决数据、备份和并发缺陷。本次不增加新集成或新功能页面。

## 工作包 A：设置状态与集成凭据

已确认的问题：布局编辑器只在管理页面首次加载时读取布局；集成变更不会同步。布局接口把停用集成投影成控件关闭，保存其他设置会永久覆盖用户的显示选择。保存请求发出后仍可编辑，但返回结果直接替换当前编辑内容。已保存集成的连接测试没有携带实例身份，掩码秘密不能解析成原凭据。

设计：

- 持久化的控件显示选择与数据源当前可用性分开表达。停用来源只阻止实际显示，不覆盖用户的显示选择；重新启用后恢复原选择。
- 集成新增、修改、启停和删除通知布局编辑器重新同步。干净编辑器可以刷新；有未保存修改时按控件 ID 保留修改，并纳入新增默认控件、移除已经删除的数据源控件。
- 保存期间禁止继续修改布局，结束后恢复控件，失败时保留编辑草稿。界面不出现“已经改了却被响应覆盖”的状态。
- 服务端采用布局版本校验，拒绝基于旧版本的全量覆盖；其他标签页修改或集成变更不能被陈旧保存静默撤销。发生冲突时保留草稿，提示重新同步，不自动覆盖服务端。
- 连接测试携带可选实例 ID。服务端仅在实例存在且类型相同的情况下复用被掩码的原秘密；新实例缺少秘密、错误实例 ID、跨类型实例均拒绝，不把秘密返回浏览器。
- 桌面布局加载失败不能阻止集成和设置恢复页面初始化，各区域独立报告加载错误。

验收：集成新增后保存宽度不丢新控件；停用再启用保持原显示选择；待保存期间没有可被丢弃的新编辑；陈旧标签页不能覆盖新布局；原凭据不重新输入也能测试连接，错误实例不能借用凭据；布局失败时恢复操作仍可使用。

主要边界：`internal/widget`、`internal/integration`、相关 `internal/httpapi` 接口，以及 `web/layout.js`、`web/integrations.js`、`web/manage.js`、`web/manage-api.js`。

## 工作包 B：采集真实性与查询复用

已确认的问题：Netdata 的 JSON `null` 解码到浮点数会得到零值，当前读取器把它当作真实零。内存、告警和 SMART 的定时任务还存在重复读取。

设计：

- 数值读取明确排除 `null` 和无效数值。若最后一个采样为空，可使用同一响应内最近的有效采样；整段无有效采样则报告不可用，不补零。真实零必须仍能显示。
- 只复用同一来源、成功且处于原刷新周期内的系统内存总量、可用内存采样和原始告警结果；缓存边界明确，过期或失败不改变旧数据成功时间。
- 告警的“忽略”过滤仅用于普通提醒；SMART 故障判定仍读取原始告警，不被忽略操作掩盖。
- 同一集成更换采集器时，旧采集器退出后新采集器才可以发布数据；新采集器的构造不提前写入共享状态，避免旧请求覆盖新配置的结果。
- 断连或实时数据过期时，在现有 NAS 标题附近显示紧凑的“数据过期”状态。浏览器请求失败也有明确提示，恢复成功后自动清除。使用已有状态和原请求周期，不新增 NAS 查询。

验收：空采样不会显示 CPU/网速为零或触发虚假的内存告警；真实零不受影响；正常情况下查询数不增加，重复查询减少；缓存过期、请求失败和集成切换不能伪造新鲜数据；被忽略的 SMART 故障仍进入硬盘健康结果。

主要边界：`internal/truenas`、`internal/integrations/runtime.go`、`internal/integration/manager.go`、`internal/state`、`internal/dashboard`、`web/view.js`。

## 工作包 C：天气降级与单位一致性

已确认的问题：首次请求失败时天气数据为未启用，天气行直接消失。刷新中任一子接口失败会中断其他接口，并丢弃本轮已获取的成功数据。英制选项存在但没有实际换算。

设计：

- 已配置并启用的天气在首次失败时仍保留占位行，显示“天气暂不可用”，不显示虚假的零度或晴天。
- 当前天气、分钟降雨、官方预警、日预报分别维护成功数据和成功时间；一个失败不阻止其他到期组件刷新，且不会增加组件的请求频率。
- 同时保留组件错误/过期状态；其他组件成功不能把失败组件标成新鲜。过期的降雨倒计时或风险提示不能继续冒充当前预测；官方预警失败不能被显示成“无预警”。
- 成功的当前天气和预报仍显示，失败组件在现有天气区域以紧凑状态说明降级，避免异常令整个天气模块消失。
- 内部温度与风速保持摄氏度和米/秒，危险提示阈值不随显示单位改变；英制仅在显示时把当前、体感和预报温度统一转换为华氏度。默认公制及用户现有显示不变。
- 不改变现有降雨、强风、紫外线提示阈值，也不新增未经数据源支持的预测。

验收：任一接口单独失败、首次全部失败、缓存过期、恢复成功均有独立测试；正常组件继续更新；正式预警和降雨提示不因其他组件刷新而被错误清除或续期；摄氏与华氏显示一致，危险判断保持一致。

主要边界：`internal/weather`、`internal/model/status.go`、`internal/state/store.go`、`internal/integrations/runtime.go`、`internal/dashboard`。

## 工作包 D：备份恢复与认证并发

已确认的问题：导出会收录崩溃遗留的原子写入临时文件，恢复却拒绝它；导出和恢复的数量及解压体积限制不同。首次设置完成接口存在并发事务竞争。修改密码和用户名没有复用重新认证的尝试限流。

设计：

- 导出和恢复共用应用文件白名单及限制：最多 2048 个文件，单文件最多 2 MiB，总解压内容最多 16 MiB，ZIP 本体最多 16 MiB。导出忽略无关文件、临时文件和恢复暂存目录；恢复继续拒绝不安全条目，不放宽白名单。
- 对完整有效的配置，成功导出的备份必须能通过恢复准备校验；超过共同限制的导出明确失败，不能生成一个以后无法恢复的包。
- 恢复继续验证管理员凭据、配置状态和引用的秘密，提交失败仍可以回滚；不在本次操作中实际恢复或重置用户的生产配置。
- 首次设置在事务提交边界串行化，并在获得排他权限后重新检查状态；不能让失败的并发请求删除成功请求的事务日志。外部连接测试不延长持久化事务的锁占用。
- 修改密码、修改用户名和重新认证共享现有 `reauth` 限流规则：同一来源 IP 最多 5 次尝试 / 10 分钟，成功验证重置预算；三种接口不能绕过共同预算。仅格式验证失败不进行密码哈希计算。

验收：临时文件残留、数量/体积边界、压缩高比例内容、路径穿越、缺失秘密、错误密码、恢复失败回滚、并发首次设置及三种认证接口交替尝试都被测试；正常设置和备份恢复不被限制误伤。

主要边界：`internal/support`、`internal/httpapi/setup.go`、`internal/httpapi/settings.go`、`internal/httpapi/server.go` 及对应测试；复用现有 `internal/auth/limiter.go`。

## 工作包 E：Windows 初始位置

已确认的问题：重启时先用 420×260 的临时窗口尺寸限制保存坐标，再按网页实际尺寸调整，会改变原来靠右的间距。

设计：

- 区分尚未得到网页尺寸的初始阶段与实际尺寸已知的阶段。初始阶段不把临时夹紧坐标保存成用户的新位置。
- 第一份有效网页尺寸到达后，用原保存位置和实际尺寸完成初始定位及屏幕边界限制；无保存位置时沿用右上角 24 像素默认间距。
- 首次实际定位完成后继续保留现有拖动保存、靠右缩放锚定及多显示器边界处理。屏幕被移除或变小时窗口仍需回到可见范围。
- 若实际尺寸一直未到达，保留可见的初始化窗口但不覆盖保存位置，并提供加载失败状态；不无限隐藏窗口。

验收：保存的靠右间距经过重启保持；无保存位置、窗口变高、超出屏幕、移除显示器及无实际尺寸消息均有核心测试；能获得 Windows 运行环境时再做 GUI 实机验证，否则明确记录未覆盖项。

主要边界：`windows/NASWallboard.Desktop/DesktopForm.cs`、`windows/NASWallboard.Desktop.Core/WindowPlacement.cs` 及核心测试。

## 验证与正式发布

每个缺陷先用回归测试复现，再修改对应实现。工作包分别通过 Go、JavaScript 或 .NET 测试后，运行全项目测试、静态检查、浏览器端测试及 GitHub CI 的竞争检测和 Windows 构建。增加的查询复用需有请求计数测试，不能仅凭代码判断“更省资源”。

最终审查检查接口兼容、秘密保护、旧配置、故障转移和恢复路径。正式更新使用经过验证的不可变镜像及配套桌面包；更新前保留现有完整配置和 compose 备份，失败则回滚。更新后核对 Wallboard 健康、数据采集、用户配置和 Home Assistant 可访问性，不以一次 HTTP 成功代替完整验收。

设计自检：每个已列出缺陷均有工作包、明确边界及验收项；没有新增查询周期，没有改动其他 NAS 服务。实施计划将按这些工作包拆分，待本设计获用户确认后再编写和执行。
